# B9_full — довідник параметрів

Повний розбір `configs/yoloe-vp-iou/ablation/B9_full.yaml`.

B9 — «повна» конфігурація трекера **YOLOe-VP-IoU** з усіма фічами (базується на
A8_full + Phase 1 High-Confidence Re-ID). Логіка трекера трифазна:

- **Phase 1** — нормальний трекінг.
- **Phase 2** — об1'єкт «під сумнівом» (починає губитися).
- **Phase 3** — повторний пошук / реініціалізація після втрати.

> Примітки з ablation-студій (2026-07-07): див. розділ «Практичні висновки» внизу.

---

## Модель та вхід

| Параметр | Значення | Що робить |
|---|---|---|
| `model_path` | `yoloe-v8l-seg.pt` | Вага YOLOe (l-версія, seg). |
| `imgsz` | `640` | Роздільність входу. Сильний важіль якості — 480 коштує ~0.14 AUC. |
| `device` | `cuda` | GPU. |

## Адаптивна впевненість детекції

| Параметр | Значення | Що робить |
|---|---|---|
| `conf` | `0.05` | Стартовий поріг conf для прийняття детекції (низький — щоб не губити слабкі кадри). |
| `conf_max` | `0.1` | Верхня межа, до якої поріг адаптивно росте по мірі впевненого трекінгу. |
| `conf_adaptive_rate` | `30` | За скільки «VPE-кроків» conf доходить від `conf` до `conf_max`. |
| `iou_threshold` | `0.2` | Мінімальний IoU з попереднім боксом, щоб вважати детекцію тим самим об'єктом (Phase 1 асоціація). |

## Збір VPE (visual prompt embeddings — банк вигляду об'єкта)

| Параметр | Значення | Що робить |
|---|---|---|
| `vpe_step` | `10` | Кожні 10 кадрів збирається новий VPE. |
| `max_vpe` | `50` | Максимум VPE в банку. |
| `vpe_conf_threshold` | `0.05` | Мінімальна conf, щоб кадр потрапив у VPE-банк. |
| `vpe_conf_max` | `0.2` | Верхня адаптивна межа цього порогу. |
| `adaptive_rate` | `500` | Темп адаптації VPE-conf порогу. |

## Керування втратою

| Параметр | Значення | Що робить |
|---|---|---|
| `max_lost_frames` | `15` | Скільки кадрів без валідної детекції терпимо, перш ніж перейти в режим повного пошуку (Phase 3). |
| `warmup_frames` | `0` | Кадри «розігріву» на старті без спец-логіки (вимкнено). |

## Phase 2 — DIoU-гейт «під сумнівом»

| Параметр | Значення | Що робить |
|---|---|---|
| `phase2_diou_threshold` | `-0.1` | Поріг DIoU для прийняття кандидата у Phase 2 (DIoU ∈ [-1,1]; −0.1 доволі поблажливо). |
| `phase2_switch_validation_frames` | `1` | Скільки кадрів підтвердження перед перемиканням на новий бокс (захист від хибних switch). |
| `waiting_reinit_conf_threshold` | `1.00` | Поріг conf для **дострокової** реініціалізації у Phase 2. `>=1.0 = вимкнено`. |
| `waiting_reinit_diou_threshold` | `-0.5` | Парний DIoU-поріг; працює лише коли попередній < 1.0 (зараз неактивний). |

## Phase 3 — повторний пошук / реініціалізація

| Параметр | Значення | Що робить |
|---|---|---|
| `reinit_conf_threshold` | `0.3` | Мінімальна conf, щоб прийняти кандидата на реініт після втрати. |
| `reinit_diou_threshold` | `-0.4` | Стартовий DIoU-гейт для реініту. Схлопує кандидатів до ≤1 — тому `phase3_appearance_weight` під B9 інертний. |
| `reinit_diou_max` | `-0.9` | Гейт адаптивно розширюється до −0.9 (чим довше загублено, тим більше області приймається). |
| `reinit_adaptive_rate` | `100` | За скільки кадрів гейт доходить від threshold до max. |
| `phase3_redetection_validation_frames` | `1` | Кадрів підтвердження перед прийняттям редетекції. |
| `phase3_vpe_freeze_frames` | `30` | Після реініту на 30 кадрів заморожується оновлення VPE (щоб не «отруїти» банк одразу після невпевненого повернення). |
| `phase3_ref_mode` | `last_valid` | Опорний бокс для DIoU у Phase 3 — останній валідний (а не anchor). |

## Phase 1 — High-Confidence Re-ID (нове в B9)

Дозволяє перехопити об'єкт навіть під час нормального трекінгу, якщо з'явилась дуже впевнена детекція.

| Параметр | Значення | Що робить |
|---|---|---|
| `phase1_high_conf_reid_threshold` | `0.9` | Потрібна дуже висока conf, щоб спрацював цей re-ID. |
| `phase1_high_conf_reid_iou` | `0.0` | Мінімальний IoU (0 = не вимагається просторове перекриття). |
| `phase1_high_conf_reid_diou` | `-0.3` | Мінімальний DIoU для прийняття. |
| `phase1_high_conf_reid_require_lost` | `false` | Не вимагає, щоб об'єкт був загублений — може перемкнутись і в активному трекінгу. |
| `phase1_high_conf_reid_validation_frames` | `3` | 3 кадри підтвердження перед перемиканням. |
| `phase1_high_conf_reid_conf_gap` | `0.15` | Нова детекція має перевищувати поточну щонайменше на 0.15 conf (захист від дрібних коливань). |
| `phase1_high_conf_reid_validation_skip` | `0` | Пропуск кадрів валідації (0 = без пропуску). |

## Експериментальний блок (внизу файлу)

| Параметр | Значення | Що робить |
|---|---|---|
| `phase3_appearance_weight` | `0.75` | Вага appearance-схожості при відборі кандидата у Phase 3: `score=(1-w)·conf+w·sim`. Під B9 інертний — DIoU-гейт лишає ≤1 кандидата. |
| `vpe_gate_threshold` | `0.75` | Поріг appearance-gate при зборі VPE. `0.75` нижчий за весь діапазон схожості → нічого не ріже, фактично вимкнений (кусає з ~0.85). |
| `vpe_gate_ref` | `aggregated` | Опора для gate — агрегований банк. Дає каскадний дрейф; `anchor` дискримінативніший, але ріже легітимні зміни вигляду. |
| `verbose` | `false` | Логування (вимкнено). |
| `debug_frame_step` | `10000` | Крок дебаг-логів (фактично ніколи). |

## Практичні висновки з ablation-студій (2026-07-07)

- **`imgsz`** — найсильніший якісний важіль: 640 → AUC 0.647, 480 → 0.503 на 9-відео наборі
  (~+14% FPS ціною −0.14 AUC). Для якісного baseline тримати 640.
- **`phase3_appearance_weight`** у поточному вигляді **нічого не змінює**: `reinit_diou_threshold: -0.4`
  схлопує кандидатів до ≤1, а коли їх кілька — max-conf збігається з max-appearance-sim. Щоб «ожив» —
  спершу послабити `reinit_diou_threshold`.
- **`vpe_gate_threshold: 0.75`** фактично вимкнений (нижчий за весь діапазон схожості). Кусати починає
  з ~0.85–0.90: допомагає на дистракторних сценах (basketball AUC 0.13→0.48), шкодить на чистих
  (tiger). Єдиний глобальний поріг не оптимальний. `vpe_gate_ref: aggregated` дає каскадний дрейф пам'яті.
